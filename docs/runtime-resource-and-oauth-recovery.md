# レンダリング資源保護とRemote MCPの再認証

## フォントキャッシュ

Runtimeのビルドは、フォント名の検索DBとは別に、標準で使用するLatin
ModernとHarano Ajiのフォントデータを事前生成します。日本語フォントには
明朝・ゴシックの標準、太字、および既定のゴシックMediumを含みます。
存在しない言語用フォントは追加インストールせず、対象環境の構成を維持します。
各フォントを別プロセスで読み、準備中に全フォントを同時保持しません。

実行時はイメージ内の解析済みデータを読み取り利用します。小さな名前検索DBの
作業用コピーは従来どおりですが、解析済みフォントデータ全体はtmpfsへコピーしません。
追加フォントの作業キャッシュはジョブ専用で、利用者間・ジョブ間では共有しません。
既存のRuntimeソースfingerprintに含まれるインストール補助スクリプトで生成するため、
変更後は別Runtimeとして扱われます。署名、Base provenance、言語選択、公開対象は変更しません。

CIの`ci-font-cache-benchmark.sh`は、使い捨てGitHub-hosted runnerだけで動作します。
同じRuntimeからフォントデータだけを除いた非公開の比較イメージと、準備済みRuntimeを
比較します。後者は新しいコンテナで2回検証し、フォントを再解析しようとしたら失敗する
Luaフックでキャッシュ利用を確認します。PDF/PNG/SVGの生成も必須です。
比較は`renderer-image`で実施し、Dailyでは準備済み側の検証だけを実行して
不要なcold比較の反復を避けます。
比較イメージ、コンテナ、出力volume、一時ファイルは終了時に削除します。

Luaの一時オブジェクト回収は標準動作を維持します。比較用の
`RENDERER_LUA_GC_MODE=balanced`は、初期化スクリプトでGC pauseを120、step multiplierを200に
設定します。ページごとの強制的な全回収や、フォント・組版機能の削除はしません。
通常のフォントcache比較では、解析済みcacheを使う標準GC・調整GC・調整GCの再実行も
比較し、初期1ページと明示取得した2ページ目のPNGが同一であることを検査します。ピークメモリが減らないという
理由だけでは不合格にせず、成果物の正常性・時間・CPU・最大メモリを合わせて判断します。
GC設定は[Luaの仕様](https://www.lua.org/manual/5.3/manual.html#2.5)に基づき、
[LuaTeXの初期化](https://texdoc.org/serve/LuaTeX/0)で適用します。

初回の[amd64/arm64比較](https://github.com/n624-dev/latex-renderer/actions/runs/39289221666)では、
標準GCが約684〜685MiB・13〜14秒、調整GCが約684〜719MiB・13〜15秒でした。
このfixtureで一貫した改善は確認できないため、調整GCを通常動作には採用しません。
同実行では準備済み3モードのレンダリングは成功しましたが、後続の2ページ目の比較が
入力の権限不整合で失敗しており、全体合格や画素一致の証拠には扱いません。
比較用PDFだけを専用の読取専用入力へコピーする修正後の
[再実行](https://github.com/n624-dev/latex-renderer/actions/runs/39392075588)では、
両アーキテクチャで2ページ分のPNG比較を含むフォント比較工程が成功しています。
同実行は後続のWorker型検査で停止しており、Source統合やCI全体の合格とは区別します。

`RENDERER_METRIC`は工程別の経過秒と、コンテナ全体の最大メモリ、累積CPU時間、
累積I/Oバイト数、工程境界で採取した一時容量を記録します。採取時の一時容量は厳密な
全瞬間の最大値ではありません。cgroup情報を取得できない環境では`unknown`とし、
0として成功判定しません。メモリ値はLuaLaTeX単体のRSSではなく、tmpfs等も含む
コンテナの値です。キャッシュによる削減率や処理時間は実測結果で判断してください。
`sampled_memory_anon_file_shmem_bytes`は工程境界での内訳です。`shmem`は`file`に含まれるため、
3値を合算して使用量にしません。最大メモリを記録した瞬間の内訳とも限りません。

## ホストの資源が不足した場合

Linux Workerは開始前に`MemAvailable`とmemory/I/O PSIを確認します。
低メモリ、memory PSI full avg10が10%以上、I/O PSI full avg10が50%以上、
またはメモリ情報が取得不能の場合、新しいコンテナを起動せずキューに残します。
確認は最大5秒に1回で、既に動いているジョブをこの判定だけで強制終了しません。

- `RENDERER_MIN_AVAILABLE_MEMORY_BYTES`: 開始に必要なMemAvailable。初期値は
  1,207,959,552 bytes（1152MiB）。正の整数を指定します。未知の入力にはこの値を
  使用し、実測済みの軽量な入力には後述の小さいsandboxに対応した値を使用します。
- `RENDERER_ADMISSION_WAIT_SECONDS`: 長時間待機の案内を出すまでの時間。初期値900秒、
  設定範囲1〜86400秒。キュー登録から数え、再起動でも起点を変えません。
  **旧版の資源待機期限とは異なり、この時間を超えたことだけではJobを失敗にしません。**

待機中は既存のJob応答の`errorCode`/`errorMessage`に`HOST_RESOURCE_WAIT`、理由、
利用可能メモリ、開始条件、長時間待機の案内を示します。Web・CLI・MCPも同じ情報を
参照します。状態は`queued`のままで、開始時には待機表示を解除します。
待機は成功したレンダリングではなく、開始時刻の保証もありません。不要になったJobは
キャンセルしてください。クライアント側の待機期限はサーバーJobの失敗とは別です。
待機中も既存の受付件数・利用者容量・Source保持・認可・キャンセル制御を適用します。

### 実測済みの軽量な入力

Workerは、sandbox外でDockerのコンテナID/PIDを確認し、そのIDに一致するcgroup v2の
`memory.peak`を実行中に観測します。コンパイルログや利用者の申告は学習元にしません。
対応するcgroupが見えない環境・短い処理・観測失敗では「不明」として既定上限を使用します。
Docker daemonがメモリ上限・swap上限のサポートを報告しない環境ではWorkerの起動を
停止します。CLIに指定しただけで上限が適用済みとは扱いません。
PDF/SVGの一部だけを再実行した結果から、全工程の見積もりを小さくすることもありません。

正常に全工程が完了した実績を、所有者・入力SHA256・entrypoint・不変Runtime・出力設定に
固定して保存します。異なる入力や利用者の見積もりは流用しません。記録はDB内に最大64件、
7日以内、16KiB未満で保持し、古い実績や壊れた記録は保守的な既定値へ戻します。
利用者データや実行中leaseの削除判断には使いません。

小さいsandbox上限は、観測ピークに128MiBを加え、64MiB単位で切り上げ、最大1GiBとします。
開始条件は「その上限＋余裕分」と既存の明示設定値の小さい方です。余裕分は128MiB以上とし、
既存設定が1152MiBより大きい場合は、その増分も引き継ぎます。未知の入力で明示設定値を
勝手に下げたり、大きく設定された他サービス用の余裕を128MiBに縮めたりしません。
128MiBは従来の1152MiB/1GiB・384MiB/256MiBの差に合わせた運用上の余裕であり、
全入力に安全だと実測で証明された値ではありません。ピーク観測も終了直前までの完全な
記録を保証しないため、見積もりは保証ではなく実際のコンテナ上限を必ず同時に適用します。
同じ入力の複数実績では最大値を使い、実OOMが起きた見積もりは無効化します。
見積もり外れによる無制限の自動再試行は行いません。

候補は一度に最大32件だけ確認し、開始可能なJobがあればそのIDだけを排他的に取得します。
開始できないページは順番に巡回するため、先頭の重いJobだけで後続全部を塞ぎません。
候補がキャンセルされても、別Jobへ黙って切り替えて同じ小さい上限を適用しません。

この事前確認はRAMの予約でもOOM防止の保証でもありません。ほかのサービスの利用量と
実際の文書の最大メモリを確認して設定してください。初回の未知の文書まで事前に正確に
分類できる仕組みではありません。コンテナは最大1GiB、swap禁止、同時1件を維持します。
カーネルの`oom_kill`増加を確認した場合は`RENDERER_MEMORY_LIMIT`として報告し、
単なるexit 137だけをメモリ不足の証拠にはしません。

## I/Oの競合を減らす

Workerはレンダリングを1件ずつ実行します。上記のI/O PSIによる開始待機と、
診断ログの非同期・上限付き直列書き込みは、重い処理やログの滞留を増やさないための制御です。
バックアップ、イメージの取得・生成、TeX配布ファイルの同期までを共通の待ち列に
入れる仕組みではありません。アプリ更新とイメージ管理のmutation lockも、
これらすべてのI/Oを排他するものではありません。

追加調整は、大量コピー・展開・フォント解析などの実行時間を調べ、定期処理の開始時刻を
ずらすところから行ってください。認証・API応答を長時間のバックグラウンド処理と同じ
排他ロックで待たせたり、容量不足時のGCや障害復旧を一律に止めたりしないでください。
I/Oの順番を調整しても、単独ジョブのメモリ不足やメモリ回収による待ちは解決しません。
判断には処理時間、memory/I/O PSI、最大メモリも使用し、CPUのiowaitだけを目標にしません。

OS側で優先度を設定する場合は、対象カーネル・デバイスでの有効性を確認します。
`IOWeight`は同じ階層のcgroup間での相対的な割り当てであり、帯域の上限ではありません。
また、Dockerクライアントを起動するサービスに設定するだけでは、別cgroupの
rootless DockerデーモンやレンダーコンテナのI/Oを制御できるとは限りません。
この変更ではディスク構成、ホスト全体の優先度、同居サービスの設定を変更しません。
詳細は[Linux cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)と
[systemdのI/O資源制御](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)を参照してください。

## OAuthの更新と再送

アクセス用トークンは10分、認可全体と更新用トークンは最大30日です。
通常はトークン更新で接続を継続するため、10分ごとの手動ログインを要求する仕様ではありません。

使用済み更新トークンの短時間の再送は、元の消費から30秒未満に限り、最新の有効な
更新結果へ合流させます。新しいトークンを余分に発行せず、再送で期限も延長しません。
記録はプロセスのメモリ内だけに最大128認可分・30秒で保持し、DBは従来どおりhashだけです。
プロセス再起動や上限到達で結果が失われた場合は、認可全体を取り消す代わりに
`temporarily_unavailable`（HTTP503、Retry-After: 1）を返します。
クライアントは最後に保存した最新の更新トークンを使い、回数制限付きで再試行してください。

30秒を過ぎた使用済みトークンの再利用は、引き続き認可全体を取り消します。
クライアント・resourceの結び付け、利用者の有効状態とsecurity version、失効・期限の
検査は再送にも適用します。正当な再送への対応は、再利用検知を無効化するものではありません。

各ツールは必要scopeを`_meta.securitySchemes`に宣言します。権限不足の場合だけ
`mcp/www_authenticate`を返し、通常のコンパイル失敗を再ログインへ変換しません。
`get_profile`は同じ利用者に対し更新・再接続後も同じ不透明なIDを返し、メールアドレス等を
必須出力にしません。接続情報の再取得が必要な場合は、接続先URLや資格情報を変更する前に
クライアント側のメタデータ更新手順を確認してください。

## 診断ログの保持

追加診断は`STORAGE_ROOT/diagnostics/`に保存し、HTTPS公開対象にはしません。
Remote MCPとWorkerの各2ファイル、1ファイル2MiB、合計最大8MiBです。
7日を超えたファイルは通常のcleanupで削除します。既存の監査ログ・成果物の保持方針、
同居サービスのjournal設定は変更しません。各JSON行も2KiB以内に制限します。
書き込みは非同期・直列で、待ち行列は最大32行です。I/Oが遅い場合は追加の診断を
捨て、認証応答をログの保存待ちにはしません。

OAuth診断には要求ID、プロセスごとにsaltを変えた認可識別子、更新世代、固定の結果分類を
残します。トークン、Cookie、認証コード、文書本文、生のエラー本文は記録しません。
ログ保存に失敗しても認可やジョブの結果を変更しません。
