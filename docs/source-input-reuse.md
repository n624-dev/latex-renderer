# 検証済みSource入力の再利用

同じ所有者の不変Sourceを繰り返し変換するとき、完全検証済みの展開結果を
読み取り専用で共有します。出力、TeXの作業領域、font cacheは共有しません。
ZIPの全検証、初回のアーカイブサイズ／SHA-256検証は維持します。

## 保存・識別・再検証

保存場所は `STORAGE_ROOT/source-trees/<tree-id>/input` です。初回の通常展開に
成功してからファイル名・サイズ・SHA-256・権限・ディレクトリ構成を記録し、
同じファイルシステム内のrenameで確定します。展開結果をもう一式コピーしません。
Source ID、所有者、アーカイブサイズ／SHA-256、検証方式と制限値を識別に含めます。
同じZIPでも異なる所有者の領域へ流用せず、同一ユーザー内の認可条件は維持します。

再利用ごとに全ファイルをストリームで再ハッシュし、名前・権限・余剰／欠落・
symlink／hardlink・別デバイス／mountを検査します。entrypointは毎回検証します。
TeXには `/work/input` のread-only bind mountだけを渡し、Job出力は独立させます。
manifestがあるという理由で内容を信頼することはありません。

破損、欠落、旧方式、制限変更、同時生成、予算不足の場合は通常のZIP検証・展開へ
戻ります。未完了のツリーは再利用しません。ZIP自体が不正ならJobを失敗させます。
容量不足で初回確定に失敗した場合は、可能なら入力を元の場所へ戻して通常処理を続けます。

## 容量・期限・回収

初期値は全体64MiB、ユーザー32MiB、最大64エントリ、取得から6時間です。
例は [renderer-io.env.example](../deploy/renderer-io.env.example) を参照してください。
既存のユーザー保存上限にも、ファイル／ディレクトリの割当ブロック、manifestと
DB用余裕を予約計上します。削除中も予約を解放せず、実体削除後に解放します。
OSの最低空きとmetadata余裕も確認します。これはCIミラーの15GiB制限とは別です。

再利用しても有効期限を延ばしません。満杯なら参照のない古いエントリを少数回収し、
それでも不足する場合はキャッシュを追加せず通常展開へ戻ります。
`SOURCE_TREE_MAX_BYTES=0` で無効化できます。ZIP制限や出力検証は変わりません。
上限を下げた場合も参照中データは削除せず、参照のないデータを次の回収で整理します。
新しい期限設定は新規作成分へ適用し、既存エントリの期限を延長しません。

共有入力にはJob／lease世代を持つ永続pinを付け、コンテナ停止確認後に解除します。
期限切れだけでpinを消しません。強制終了後は通常Jobの回復に加え、正確な名前の
旧コンテナが停止したことを確認してからpinを回収します。Dockerが不明なら保護します。
Workerの15分間隔の回収と既存の毎時cleanupが同じ回収処理を使い、未完了／期限切れ／不要な
エントリをDBロック下で削除対象へ切り替え、再帰削除はロック外で行います。
Worker停止中もpinのない残骸はタイマーで回収されます。状態不明のpinが残った場合は
Worker回復を確認し、DB行を手動で消して保護を回避しないでください。

## 計測・試験

[I/O計測](renderer-io-performance.md) は完全展開と全ファイル再検証を分けて記録します。
通常テストは小さなZIP、独立Job、複数entrypoint、破損、予算不足、ENOSPC注入、
参照とGC、停止不明、再起動回復、外部symlinkへの削除防止を確認します。
実TeXのPDF／PNG／SVG比較は使い捨てCI Runtimeで実行し、fixture結果と区別します。
