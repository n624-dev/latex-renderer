## LAN の IP アドレスからアクセスする

Akebi は、サーバーのプライベート IP アドレスをホスト名に変換して HTTPS 接続を実現します。

共通の証明書サービスを使う場合は、LaTeX Renderer サーバーのウィザードで設定します。証明書サービスを自分で提供する場合は [Akebi の運用手順](/docs/lan-https-authority/)へ進んでください。

- **IPv4 の例**：サーバー IP が `192.168.1.50`、LAN ドメインが `lan.example.org` の場合、`https://192-168-1-50.lan.example.org` になります。
- **IPv6**：対応するプライベートアドレスの 8 グループを展開したホスト名になります（実際の接続にはセットアップ画面に表示された URL をそのまま使ってください）。

**ネットワークと DNS の前提**：
クライアント端末からサーバーが属する LAN へ通信できる必要があります。名前解決ができない場合は、ルーターや DNS リゾルバーの **DNS リバインディング保護**（プライベート IP を返す DNS 応答の遮断機能）が働いていないか確認し、必要な場合は使用する LAN ドメインだけを例外に追加してください。

## 証明書の方式を選ぶ

| 方式 | 必要なもの・特徴 |
| --- | --- |
| **共通サービス・公開 CA** | 共通サービスの設定と公開 CA 規約への同意。証明書の秘密鍵はサーバー手元に保存される |
| **独自サービス・公開 CA** | [独自の Akebi 証明書サービス](/docs/lan-https-authority/)の URL と LAN ドメイン（招待制の場合は招待コード） |
| **Keyless** | Keyless 対応の証明書サービス。TLS ハンドシェイク時の署名を証明書サービス側へ委任する |
| **手持ちの証明書・プライベート CA** | サーバー名に一致する証明書と秘密鍵。プライベート CA の場合は接続する全端末とサーバーにルート CA の信頼設定が必要 |

> [!NOTE]
> - 公開 CA を利用すると、発行された証明書のホスト名は公開の **Certificate Transparency（CT）ログ**に記録されます。
> - 異なる拠点の LAN であっても、同じプライベート IP アドレスと同じ LAN ドメインの組み合わせを使うとブラウザ上は**同一オリジン**として扱われ、Cookie などの保存領域を共有する点に注意してください。

## LAN 向けに設定する

1. 新規構築の場合は [サーバーの準備](/docs/self-hosting/#準備するもの)を済ませ、`sudo n624-latex server setup --web` で [ウィザード](/docs/server-setup/#ブラウザで開く)を起動します。管理下の専用 HTTPS で運用中のサーバーを切り替える場合は `sudo n624-latex server setup --ingress --web` を使います。
2. 公開経路で **LAN** を選び、使用するネットワークインターフェース、プライベート IP アドレス、接続を許可するサブネット範囲、HTTPS ポートを指定します。
3. 証明書サービス（共通または独自）と証明書の方式を選びます。公開 CA を使う場合は CA 規約を確認し、招待制の独自サービスを使う場合は招待コードを入力します。
4. プレビューで生成される HTTPS URL と許可サブネットを確認して適用します（アプリ側のパスワード認証や OIDC 認証はそのまま併用されます）。
5. 許可したサブネット内の別端末からその HTTPS URL を開き、証明書警告が出ずにログインとサンプル変換ができることを確認します。

独自の証明書サービスを建てる場合は、[Akebi の証明書サービスを自分で運用する](/docs/lan-https-authority/)を参照してください。

## 証明書の状態を確認する

稼働状態と自動更新タイマー、専用ネームスペースのログは次のコマンドで確認できます。

```bash
systemctl status latex-renderer-lan-https.service latex-renderer-lan-renew.timer
sudo journalctl --namespace=latex-renderer-lan --since '1 hour ago'
```

発行や更新に失敗した場合は、サーバーのシステム時刻のズレ、証明書サービスへの HTTPS 疎通、ドメインと IP の設定、CA が返す再試行待機時刻を確認してください。一時的に更新が失敗しても有効期限内の既存証明書は維持され、次回のタイマー実行時に記録済みの発行処理から再開します（秘密鍵と発行状態が食い違う場合は、保管されている同じ世代の状態ファイルを確認してください）。

詳細資料：[Akebi の設計・詳細な障害対応](https://github.com/n624-dev/latex-renderer/blob/main/docs/akebi-lan-https.md)
