## Что сохраняется {#何が保存されるか}

| Тип | Содержимое | Назначение |
| --- | --- | --- |
| **Периодическая резервная копия** | База SQLite и входные ZIP, используемые активными ревизиями, черновиками и создаваемыми предварительными просмотрами | Защита базы, проектов и редактируемых документов |
| **Точка восстановления при обновлении** | SQLite непосредственно перед обновлением, всё хранилище приложения и сведения о прежней версии | Расследование сбоя и восстановление прежнего состояния |
| **Отдельная копия конфигурации хоста** | Файлы наподобие `/etc/latex-renderer/`, закрытые ключи, сертификаты TLS и состояние Akebi | Воссоздание хоста после отказа |

- После восстановления периодической копии откройте проект в редакторе, чтобы заново создать предварительный просмотр. Результаты временных заданий и рабочие кеши не включаются.
- Отдельно защитите конфигурацию, сертификаты и ключ расшифрования (идентификатор age). **Храните зашифрованные резервные копии и ключ в разных защищённых местах, чтобы не потерять оба при одном происшествии.**

## Создание копии вручную {#手動で作成する}

1. Войдите как владелец и откройте **Администрирование → Система → Резервные копии**.
2. Нажмите **Создать резервную копию** и дождитесь завершения.
3. Нажмите **Проверить последнюю копию** и проверьте имя архива и время последней проверки. Ключ расшифрования должен находиться на сервере.

### Создание и проверка из командной строки {#コマンドで作成-検証する}

1. Немедленно создайте зашифрованную копию на сервере. В `/etc/latex-renderer/backup.env` параметр `BACKUP_DIRECTORY` указывает каталог назначения, по умолчанию `/var/lib/latex-renderer/backups`. За периодическое создание копий отвечает таймер `latex-renderer-backup.timer`.

```bash
sudo systemctl start latex-renderer-backup.service
sudo journalctl -u latex-renderer-backup.service -n 20 --no-pager
```

2. Скопируйте файл `.tar.age` на проверочный хост Linux. Подготовьте GNU `tar`, `age`, поддерживаемую версию Node.js (24 или 26) с `node:sqlite` и ключ расшифрования. Для долговременного хранения разместите архив и ключ отдельно.
3. [Скачайте, проверьте и распакуйте серверный дистрибутив](/ru/docs/self-hosting/#v1-6-9をダウンロードして検証) той версии, которой создана копия. Укажите версию в первом `version=`, задайте для `release_dir` распакованный каталог и выполните скрипт из дистрибутива.

```bash
release_dir=/path/to/verified-release
BACKUP_AGE_IDENTITY_FILE=/path/to/age-identity \
  node "$release_dir/deploy/scripts/restore-test.mjs" /path/to/backup.tar.age
```

Сообщение `restore_test.completed` означает, что проверка завершена. Тест проверяет целостность SQLite и распакованных во временном каталоге входных ZIP. Чтобы проверить внешнюю копию, получите архив из места его хранения.

## Проверка точки восстановления после сбоя {#更新失敗後の復旧点を確認する}

Если после неудачного обновления появляется `RECOVERY_REVIEW_REQUIRED`, проверьте состояние точки восстановления с административными правами.

```sh
sudo n624-latex server recovery status
```

> [!DETAILS] 履歴資料　Просмотр состояния в старых версиях
>
> Если `n624-latex server recovery status` отсутствует, выполните `sudo /usr/local/bin/node /usr/local/libexec/latex-renderer-update-recovery.mjs status`.

1. Сопоставьте идентификатор точки (`POINT_ID`), версии приложения и программы обновления, схему базы и запущенные службы. Если данные нужно восстанавливать, сначала сохраните архив и текущую конфигурацию в отдельном месте.
2. Выполняйте `acknowledge` лишь после расследования, когда подтверждено, что данные восстанавливать не требуется и защиту точки можно снять.

```sh
sudo /usr/local/bin/node /usr/local/libexec/latex-renderer-update-recovery.mjs acknowledge POINT_ID
```

`acknowledge` завершает проверку и при выполнении условий возобновляет работу служб. При восстановлении данных оставьте точку защищённой и перейдите к следующей процедуре.

## Восстановление данных {#データを復旧する場合}

Изменения после создания копии будут потеряны. Если база совместима и достаточно откатить приложение, воспользуйтесь [возвратом к прежней версии в разделе обновлений](/ru/docs/updates/#前の版へ戻す). Опробуйте восстановление данных на тестовом хосте, прежде чем выполнять его в рабочей среде.

1. **Определите цель и сохраните текущее состояние.** Найдите архив и версию приложения, совместимую с его схемой. До вмешательства в рабочую среду отдельно сохраните текущие базу, хранилище и конфигурацию.
2. **Остановите службы.** Удерживая общую административную блокировку, остановите все службы и таймеры, записывающие в базу или хранилище, чтобы избежать конфликтов с обновлением и очисткой.
3. **Распакуйте и проверьте.** Расшифруйте архив, извлеките его в пустой закрытый каталог и проверьте целостность. Для точки обновления также сравните управляемый root файл `summary.json` с внутренним манифестом.
4. **Восстановите данные на один момент.** SQLite и хранилище входных и выходных файлов должны происходить из **одной точки восстановления**. Для периодической копии положите каждый ZIP по проверенному пути `storage_key` из восстановленной базы. Используйте соответствующие версии, конфигурационные файлы, владельцев и права.
5. **Запустите и проверьте.** Проверьте вход, преобразование сохранённого проекта, скачивание результатов и создание новой копии. Если экспорт аудита остановится из-за несовпадения позиции, следуйте процедуре [восстановления журналов аудита](/ru/docs/reference/#監査ログの復旧).

См. [Формат и проверки эксплуатационных копий](https://github.com/n624-dev/latex-renderer/blob/main/OPERATIONS.md#backup-and-restore-boundaries) и [Устройство точек восстановления при обновлении](https://github.com/n624-dev/latex-renderer/blob/main/docs/update-recovery.md).
