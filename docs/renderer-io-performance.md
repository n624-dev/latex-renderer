# レンダリングのI/O計測

`renderer-image` の手動実行で `io_benchmark: true` を指定すると、検証済みの
一時Runtimeを再利用し、1・10・50・100ページのPDF／PDF+SVGを計測します。
比較試験は使い捨てのGitHub-hosted Runner専用です。共有サーバーでは実行しません。
生成ファイルは終了時に回収し、永続的なActions cacheは追加しません。

## 編集間のコンパイル作業キャッシュ

TeX Live 2026-11-22 のamd64 Baseから、英語と日本語コレクションを入れた
Runtimeを作り、Ubuntu 24.04の使い捨てKVMで計測しました。VMは3 vCPU・
4 GiB RAM、各コンテナは1.5 CPU・1 GiBです。数式、参照、BibTeX、TikZを含む
合成文書で本文だけを書き換え、空の出力領域からの処理と、直前のコンパイルの
補助ファイルを使う処理を比較しました。pLaTeXとupLaTeXには日本語を含めました。

次の各セルは、コンテナ起動から成果物回収までの経過秒数です。各条件を1回ずつ
測定しました。ブラウザーへの転送やジョブの待機は含みません。

| エンジン |     1ページ |    10ページ |    50ページ |   100ページ |
| -------- | ----------: | ----------: | ----------: | ----------: |
| LuaLaTeX | 5.36 → 2.61 | 5.42 → 2.57 | 5.52 → 2.64 | 5.71 → 2.71 |
| pdfLaTeX | 3.37 → 1.77 | 3.37 → 1.79 | 3.49 → 1.78 | 3.63 → 1.84 |
| XeLaTeX  | 3.83 → 2.13 | 3.86 → 2.12 | 3.90 → 2.15 | 4.03 → 2.12 |
| upLaTeX  | 3.58 → 2.08 | 3.59 → 2.12 | 3.70 → 2.13 | 3.78 → 2.12 |
| pLaTeX   | 3.50 → 2.03 | 3.51 → 2.04 | 3.59 → 2.07 | 3.73 → 2.10 |

全20ケースでページ数、PDFから抽出した本文、45 DPIで描画した全ページの
画像が一致しました。補助ファイルは1件あたり12,092〜21,931 bytesでした。
コンテナのCPU時間は約50〜60%減り、測定した最大メモリは約185 MiBから
約184 MiBでした。補助ファイル再利用の効果は文書によって異なります。

同じ変更のWebビルドから取得したgzipファイルは、エディターが124,237 bytes、
選択言語の辞書が1,708〜2,416 bytes、PDF.js本体とWorkerがそれぞれ
156,664 bytesと396,859 bytesでした。エディターは編集画面を開いた時点で
読み込みます。狭い画面ではPDFタブを開くまでPDF.jsを読み込まず、PNG表示
から開始した場合もPDF.jsを取得しません。

再計測する場合は、使い捨てホストにDockerとPopplerのコマンドを用意し、
検証済みRuntimeを指定してください。サービス運用中のホストでは実行しません。

```sh
RENDERER_DISPOSABLE_BENCHMARK=1 sh deploy/scripts/benchmark-draft-engines.sh latex-renderer:test
```

キャッシュは`DRAFT_WORK_CACHE_BYTES`で有効にできます。既定では無効です。
設定の上限と回収については[運用手順](../DEPLOYMENT.md)を参照してください。

## エディターで最初のページを表示するまで

所有者がエディターでPDFを表示すると、ブラウザーは必要なバイト範囲を取得
できます。取得ごとに認証とダウンロード中の削除保護が適用されます。PDFは
引き続き `private, no-store` です。エディターのスクリプト・CSS・辞書・
PDF.jsの補助ファイルには内容のSHA-256を含むURLを使い、ブラウザーが1年間
再利用できます。公開資産が変わるとページに新しいURLが入ります。

ChromiumのローカルHTTP試験では、1,620,518 bytesの合成PDFの先頭ページに
必要だった本文は113,190 bytes、範囲リクエストは2件でした。1画素の試験用
PNGは69 bytesです。同じブラウザーで2ページを開き、共通CSSの要求が1回
であることも確認しました。初回PDFの処理にはPDF.jsとWorkerの初回読み込み
が入ります。文書構造、キャッシュ、通信速度、PNGの生成待ちで結果は変わります。

pdfLaTeXで組版した10ページの文書2本を、Ubuntu 24.04のChromiumで3回ずつ
計測しました。PDFと最初のページのPNGは同じ組版結果から配信しました。
時間は初回表示までの中央値です。PNGは初回要求時にPopplerで150 DPIの画像を
生成しています。バイト数は成果物の本文のみです。

| 文書 | PDF全体 | PDFの初回転送 | PDF表示 | PNGの初回転送 | PNG生成 | PNG表示 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 文章と数式 | 69,922 bytes | 69,922 bytes | 335 ms | 37,530 bytes | 79 ms | 173 ms |
| ページごとに画像を含む | 19,483,667 bytes | 2,051,091 bytes | 328 ms | 654,544 bytes | 127 ms | 227 ms |

画像付きPDFは範囲リクエスト5件で先頭ページを表示しました。localhostでの
比較で、実環境の通信遅延やWorkerのキュー待ちは含みません。
[計測実行](https://github.com/n624-dev/latex-renderer/actions/runs/45538009393)

- ブラウザーのPerformanceパネルで `latex-renderer:editor:input-idle`、
  `save-and-queue`、`pdf-load-and-paint`、`png-load-and-paint` の
  直近の計測を確認できます。転送量とサーバー応答時間はNetworkパネルで確認
  できます。
- Workerの `renderer_worker.draft_preview_completed` は、投入から動作開始
  までの `queueAndPrepareMs`、そのうち入力準備の `sourcePrepareMs`、
  コンパイル用コンテナの経過、成果物検証、確定処理、作業キャッシュの利用を
  記録します。Workerの既存診断ローテーションを使用します。
- CIミラーの新規公開時は `estimatedPeakBytes` と、GC前後に実際に割り当て
  られていたバイト数を記録します。前者は同期を許可した時点の見積もりで、
  後者は各時点の観測です。使用量にはハードリンクした内容を一度だけ数えます。

ブラウザー試験はビルド済みのWebを使って再現できます。

```sh
pnpm --filter @latex-renderer/web build
EDITOR_PREVIEW_BENCHMARK=1 pnpm exec vitest run --disableConsoleIntercept --config vitest.browser.config.ts tests/browser/project-editor.browser.ts
```

英語・日本語コレクションを含むRuntimeでは、5エンジンの通常文書と回転した
数式、およびpLaTeXとupLaTeXの縦組文書でPDF・PNG・SVGを確認できます。
回転・縦組の試験数式はSVGに残り、位置を確定できない場合は
`placementStatus: "unknown"` を返します。

```sh
RENDERER_SMOKE_GEOMETRY=1 sh deploy/scripts/smoke-test-renderer-engines.sh latex-renderer:test
```

CIの手動I/O計測でも、この追加の組版確認を実行します。

## 基準値

[基準実行](https://github.com/n624-dev/latex-renderer/actions/runs/39194458574)
（amd64、TeX Live 2026-10-17、コミット `e8fff10`）の全ページPNG生成方式です。
比較用文書の値であり、実サービスのすべての文書を代表するものではありません。

| ページ | PDF全体 | PDF+SVG全体 |         PNG合計 | PDF成果物の検証・公開 |
| ------ | ------: | ----------: | --------------: | --------------------: |
| 1      |     2秒 |         3秒 |    13,655 bytes |                 6.9ms |
| 10     |     2秒 |         4秒 |   139,558 bytes |                12.1ms |
| 50     |     5秒 |         7秒 |   721,788 bytes |                33.5ms |
| 100    |     8秒 |        12秒 | 1,456,392 bytes |                56.5ms |

100ページではPNG生成だけで6〜7秒を使用しました。プレビューの必要時生成と、
成果物検証の読み直し削減は、異なる工程の改善です。

必要時生成のAPI・クライアント・容量と復旧の条件は
[PDFプレビュー](lazy-previews.md) を参照してください。
新方式の比較は同じPDFから全ページを生成する対照と、初回／要求ページのバイト比較を含みます。
比較結果が得られる前に改善率を保証することはありません。

[必要時生成の比較実行](https://github.com/n624-dev/latex-renderer/actions/runs/39206403150)
（amd64、TeX Live 2026-10-17、`8245c9d`）は全体が成功しました。
旧方式の対照は、同じRuntimeと同じ完成PDFから全ページをPNG化しています。

| ページ | 新PDF全体 | 新PDF+SVG全体 |            初回PNG | 同一PDFの全ページPNG対照 |
| ------ | --------: | ------------: | -----------------: | -----------------------: |
| 1      |       1秒 |           3秒 | 13,655 bytes / 1枚 |       13,655 bytes / 1枚 |
| 10     |       2秒 |           4秒 | 13,655 bytes / 1枚 |     139,558 bytes / 10枚 |
| 50     |       3秒 |           4秒 | 13,655 bytes / 1枚 |     721,788 bytes / 50枚 |
| 100    |       2秒 |           5秒 | 13,655 bytes / 1枚 |  1,456,392 bytes / 100枚 |

全8ケースで初回PNGと明示要求した最終ページのPNGが、全ページ生成した対照と
バイト単位で一致しました。100ページの全ページPNG対照は8秒・約8.2CPU秒でした。
初回生成の削減効果を示す単発比較であり、別実行の基準値との時間差をすべて
本変更の効果とはみなしません。カーネル・キャッシュ・Runnerの変動を含みます。

## 検証済みSourceの読み取り専用再利用

[比較工程](https://github.com/n624-dev/latex-renderer/actions/runs/39206552434)
は成功しましたが、この実行全体はテストimportの不備で失敗しています。
同じRunner上の3回の中央値です。ページキャッシュが温まった条件であり、
冷間I/Oや本番の待ち時間を保証する数値ではありません。

| Source                   | 完全検証＋展開 | 全ファイル再検証 | 初回展開＋manifest記録 | 追加保持する入力 |
| ------------------------ | -------------: | ---------------: | ---------------------: | ---------------: |
| 小規模3ファイル          |         3.74ms |           2.17ms |                 7.07ms |        195 bytes |
| 402ファイル              |       232.07ms |          93.29ms |               332.48ms |    409,731 bytes |
| 16MiB画像を含む3ファイル |        54.10ms |          14.26ms |                61.67ms | 16,777,347 bytes |

再検証工程の追加書き込みブロックは0でした。保持量の表は論理サイズであり、
実際の予算には割当ブロック・ディレクトリ・manifest・DB余裕を含めます。
初回負担と追加保存量があるため、容量上限と期限なしの保存にはしません。
実装条件は [Source入力の再利用](source-input-reuse.md) を参照してください。

## 成果物の単一パス検証

[比較実行](https://github.com/n624-dev/latex-renderer/actions/runs/39195818639)
のベンチマーク工程は成功しましたが、この実行全体はlintで失敗しています。
成功したCI全体の結果としては扱いません。

同一fixtureの走査・形式検証・SHA-256・コピー・コピー後の照合を比較した結果です。
各fixtureは4MiBのPDF、100個のSVG、指定数のPNGを含みます。

| PNG数 | 従来方式 | 単一パス＋CoW要求 | CoWの実対応        |
| ----- | -------: | ----------------: | ------------------ |
| 1     |  148.5ms |           118.1ms | 非対応・通常コピー |
| 20    |  166.3ms |           115.4ms | 非対応・通常コピー |
| 100   |  259.2ms |           218.5ms | 非対応・通常コピー |

この単発比較では単一パス方式が速く、出力の全SHA-256も一致しました。
順序・ページキャッシュ・ファイルシステムによる変動があるため、一定の改善率は保証しません。
CoW対応ファイルシステムでの高速化は、この結果では未検証です。

既定の検証は同じファイル記述子で署名部・SVG構造・SHA-256を検査します。
SVGは逐次解析し、PDF／PNG／SVGを追加の全量バッファには読み込みません。
走査後のinode・リンク数・サイズ・更新時刻が変化した場合は拒否します。
候補へのコピーには `COPYFILE_FICLONE | COPYFILE_EXCL` を指定します。
CoW非対応時の通常コピーは[Node.jsの定義](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromisescopyfilesrc-dest-mode)に従い、
容量不足・既存ファイル・その他のコピー失敗を成功には置き換えません。
ハードリンク共有、検証の省略、確定世代の上書きは行いません。

## 指標の読み方

- `RENDERER_METRIC` は工程の経過秒、コンテナの累積CPU・I/O・メモリ高水位、
  工程境界での一時容量を記録します。経過秒は1秒単位であり、一時容量は厳密な最大値ではありません。
- `RENDERER_IO_BENCHMARK` はNode側のwall／CPU／カーネルI/Oブロック数と
  scan／format／hash／copyを記録します。最大RSSはそのプロセスの生存期間の高水位です。
- 通常CIでは小規模Source3種と成果物fixtureを比較します。
  実際のTeX比較には上記の任意実行を使い、変更前後のcommit・architecture・日付を揃えます。
- 生成物の全バイト照合は比較試験にも含めます。速さだけを理由にvalidationを省略しません。
